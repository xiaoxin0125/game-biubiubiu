# 静态资源托管与带宽优化（操作手册）

> 站点出口带宽很小（沿用原有记录的 6 Mbps ≈ 0.75 MB/s），而模拟器核心、游戏镜像
> 都是几十 MB 的大文件。本手册说明**已经实现**的优化与托管方式、上线步骤、验收方法
> 和回滚办法。
>
> 相关现状另见 `deploy/README.md`（部署）、`deploy/STUN.md`（中继）。
> 文中凡是"实测"都是在本机跑出来的数字；凡标注"待核实"的是需要你在上线前确认的条件。

## 一、结论

1. 核心（libretro 的 js/wasm）**可以托管到别的服务器**，主站保留同一份作为回退。
2. 但**性价比最高的一步是本机 gzip**：核心总量 102 MB → 31 MB，不用第二台机器、
   不用改代码、不需要重新构建前端。
3. ROM 也提供了浏览器直连（短期签名地址）的方式，**默认关闭**，先在远端服务补上
   签名接口、验收通过后再打开开关。
4. 加载进度已经做成界面的一部分：核心 / 当前 ROM / 父版本 ROM / BIOS 各自显示
   "下载中 / 本地缓存已就绪 / 校验中 / 切换备用地址 / 已跳过"，并给出总体百分比。

## 三、客户端缓存现状（决定优化上限）

- **HTTP 层**：版本化核心地址带 `public, max-age=31536000, immutable`。
- **应用层**：核心与 ROM 都存进 IndexedDB，缓存键是**逻辑标识**：核心用
  `core:<发布版本>:<文件名>`，ROM 用原始同源 URL。换服务器地址不会重复存一份，
  换版本号则等于强制更新。
- 结论：100 MB 是"每个浏览器第一次"的成本，老用户回访为 0。带宽压力集中在
  **新用户首次进游戏、换设备/清缓存**。
- 顶部栏「清空本地缓存」只清 IndexedDB；HTTP 缓存里的核心文件靠**换版本号**失效
  （URL 变了，自然不再命中）。

## 四、核心资源：发布 → 同步 → 开关（已实现）

### 4.1 数据流

```
deploy/build-cores.mjs                deploy/sync-cores.sh              后台「站点设置」
data/cores ──▶ data/cores-dist/<版本>/ ──▶ 资源服务器 /releases/<版本>/ ──▶ 启用远端核心托管
              （含 .gz/.清单）                （HTTPS + CORS）
                                                   │
浏览器 ── 直接取  https://资源服务器/<版本>/<文件>  │
   └── 失败/未开启 ─▶ 主站 /api/cores/<版本>/<文件> ┘（Node 读取，按清单校验体积）
```

版本号 = 这批核心内容摘要的 12 位十六进制。**同一个版本号下的字节永远不变**，
所以可以放心给一年 `immutable` 缓存；核心更新 → 新版本号 → 新目录 → 旧目录留着回滚。

### 4.2 本机构建与发布

```bash
cd /www/wwwroot/xbw.ppxin.com
node deploy/build-cores.mjs            # 生成 data/cores-dist/<版本>/（.gz + manifest.json）
node deploy/build-cores.mjs --prune    # 顺手清理旧版本目录（默认保留 2 个）
```

- 输出目录 `data/cores-dist` 已加入 `.gitignore`（本机约 134 MB，可再生）。
- 重复构建同一批文件不会产生新目录；改一个字节就会得到新版本号。
- 主站**不需要**再留一份发布副本：`data/cores-dist` 缺失时会按清单体积校验后
  顶用 `data/cores` 里的同名文件，宁可不发也不发内容不符的文件。

### 4.3 打开 nginx 的 wasm 压缩（必做，一行）

`/www/server/nginx/conf/nginx.conf` 的 `gzip_types` 里没有 `application/wasm`，
所以 34 MB 的 wasm 是**明文**传的：

```bash
sudo cp /www/server/nginx/conf/nginx.conf /www/server/nginx/conf/nginx.conf.bak-$(date +%Y%m%d%H%M)
sudo sed -i 's#text/x-js;#text/x-js application/wasm;#' /www/server/nginx/conf/nginx.conf
sudo /www/server/nginx/sbin/nginx -t && sudo /www/server/nginx/sbin/nginx -s reload
```

- `gzip_proxied expired no-cache no-store private auth` 这一行**不影响**：它只作用于带
  `Via` 头的请求（CDN 回源），浏览器直连不带 `Via`。
- 主站的 `/api/cores/*` 刻意继续交给 Node（Node 负责版本与体积校验），压缩靠全局
  gzip；**不要**在主站再加 `/api/cores/` 的 `gzip_static` 静态直出：那会绕过版本校验，
  也容易出现".gz 与 .wasm 不是同一批"的陈旧缓存。
- 预压缩（`gzip_static`）留给远端资源服务器，那里的版本目录由脚本原子发布，不会出现
  与源文件不同批的情况。

### 4.4 远端资源服务器

远端站点配置模板见 **`deploy/nginx/remote-cores.conf`**（要点：HTTPS、只允许 GET/HEAD、
`gzip_static on`、`Access-Control-Allow-Origin: *`、成功响应才带一年 `immutable`）。
站点根目录 `/www/wwwroot/cores`，发布目录是 `releases/<版本>/`。

如果这台机器是 NAT 机、只有个别映射端口，或者要在同一台机器上同时提供核心与 ROM，
用另外两个模板（它们是"塞进已有站点 server{} 里"的片段/整段，二选一）：

- `deploy/nginx/php-rom-upload-site.conf`：这台机器上跑 **PHP 版 rom-upload**（nginx
  自己就是 rom-upload），额外加一个 `/releases/` 静态段。只需要一个端口，推荐。
- `deploy/nginx/remote-cores-and-rom.conf`：保留 **Node 版** rom-upload 时用，nginx
  监听另一个端口，`/releases/` 静态 + `/rom/` 反代到 Node。

配置里几条容易踩的：`listen` 不能和 `proxy_pass` 同端口；`server_name` 要包含 CDN 加速的
域名（回源默认带该 Host）；伪静态里已有 `location /` 时不要再写一个；站点根目录若指向
rom-upload 项目目录，务必 deny `config.json`（里面有 token）。

CDN（腾讯 EdgeOne）侧：**回源协议要选 HTTP**——"跟随客户端"会让 https 回源打到没有 443
的源站，表现为整站 521；核心文件可以长缓存，但 `/signed/...` 绝不能配"忽略查询串"的缓存。

同步（在本机执行）：

```bash
CORES_SSH=root@<资源服务器> CORES_SSH_KEY=~/.ssh/<私钥> \
CORES_REMOTE_DIR=/www/wwwroot/cores/releases \
deploy/sync-cores.sh
```

脚本行为：先传到 `.staging-<版本>/` → 远端逐个核对体积与 sha256（含 `.gz`）→
`mv` 成最终目录。**不使用 `rsync --delete`**，旧版本目录保留，回滚只需改回旧版本号。

### 4.5 后台开关

「站点设置 → 核心资源（远端托管）」：

- **启用远端核心托管**：关 = 强制用本机核心（同时忽略环境变量里的旧值）；
  开 = 使用下面的地址。改完刷新页面生效（新打开/刷新的页面直接读新配置，不需要重新构建）。
- **远端核心地址**：如 `https://cores.example.com/releases`。必须能被玩家的浏览器
  打开：https + 允许跨域读取。
- 地址与开关是**两个独立设置**：开关关着也能把地址保存下来，随时可以改，测通了再打开
  开关即可，不需要反复重填（改动前的老数据里没有开关字段，那时"保存 `none`"等于关闭，
  读取时仍按地址推断，行为不变）。
- **测试远端核心**：用当前浏览器实测，报告
  - 公开发布清单的 HTTP 状态；
  - 远端版本与本站版本是否一致（不一致说明远端需要重新同步）；
  - 抽样一个 `.wasm`：content-type、是否命中 gzip 预压缩副本、体积。
  跨域被拦时 fetch 只会抛 `TypeError`，这里会把常见原因写出来。

也可以用环境变量兜底（`VITE_CORES_BASE_URL`，见 `server/config.js` 白名单）。
优先级：**后台开关 > 地址里的 `none` 哨兵（老数据） > 环境变量**；开关关掉即强制本机，
环境变量不再生效。

### 4.6 主站接口

| 接口 | 作用 |
|---|---|
| `GET /api/cores/manifest` | 当前发布版本 + 每个文件的 `size` / `sha256` / `gzipSize` |
| `GET /api/cores/<版本>/<文件>` | 版本化地址（远端不可用时的回退），文件来自 `data/cores-dist` 或按清单校验的 `data/cores` |
| `GET /api/cores/<core>.js` / `.wasm` | 历史地址，保留兼容（老页面、本地开发） |
| `GET /api/cores/<core>_libretro.js` / `.wasm` | 历史别名，仍然可用 |

## 五、BIOS：条件缓存（已实现）

原来每次开局都重下整套 BIOS（街机 4.84 MB、PSX 2.50 MB）。现在：

- 后端：先鉴权，再带 `ETag`（体积 + mtime）与 `Cache-Control: private, no-cache`；
  客户端带 `If-None-Match` 命中时返回 **304**，不传文件正文。
- 前端：不再强制 `cache: 'no-store'`，因此"每次开局重下"变成"每次开局一次轻量校验"。
- 语义：`private` 是因为内容只给登录用户；`no-cache`（每次都校验）换来"换掉 BIOS
  文件立刻生效"，不需要靠改文件名或等缓存过期。
- BIOS 仍然**不进 IndexedDB**（过期的归档字节会造成难查的 CRC 问题），且仍留在主站：
  它是登录后才有权限的资源，迁出需要另配一套受保护的下载通道。

## 六、ROM：浏览器直连（默认关闭）

### 6.1 流程

```
浏览器 ── GET /api/roms/:id/file ─▶ 主站（鉴权 + 权限判断）
                                     ├─ 未开启直连：带密钥回源、边下边传（现状）
                                     └─ 已开启直连：302 → https://远端/signed/<id>?exp=&sig=
浏览器 ── 跟随 302 ─▶ 远端：校验签名 → 只读该文件（支持 Range / HEAD）
```

- 签名算法（主站、Node 版、PHP 版三处一致）：
  `sig = HMAC-SHA256(secret, 'download.<文件id>.<exp>')`，`exp` 为 Unix 秒。
- 有效期 `600` 秒，允许 60 秒对表误差，并拒绝"把 exp 推到很远的未来"。
- 上传/删除用的 `X-Token` **永远不下发到浏览器**；下载用的是另一个密钥。
- 浏览器缓存键仍是原始同源 URL `/api/roms/:id/file`，所以**签名每次都变也不影响
  老用户命中 IndexedDB**。
- 直连关闭、或地址/密钥不全、或记录没有远端 id 时，自动回到本机代理回源。

### 6.2 远端服务补签名接口

Node 版与 PHP 版都新增了只读入口 `GET|HEAD /signed/<id>?exp=&sig=`（CORS 已带上）。
本机的两个副本已经打好补丁：

- `rom-upload-php/index.php`（本仓库内）
- `/www/wwwroot/rom-upload/server.js`（同级项目，已改，需要重启该服务生效）

**资源服务器那台机器上的同一份服务也要打上补丁**，带上目标文件路径执行：

```bash
node deploy/patch-remote-signed.mjs /www/wwwroot/rom-upload/server.js
node deploy/patch-remote-signed.mjs /www/wwwroot/rom-upload-php/index.php
```

补丁脚本：幂等（已打过就跳过）、锚点必须唯一命中（否则整体放弃、不写文件）、
写入前留 `.bak-<时间戳>` 备份。验收：

```bash
# 期望 200/206 且带 access-control-allow-origin；无签名、改 exp、换密钥都应 403
curl -s -o /dev/null -D - "https://<资源服务器>/signed/<32位id>?exp=<秒>&sig=<hmac>"
```

### 6.3 后台开关

「站点设置 → 远端存储（大 ROM）」：

- **下载地址（浏览器直连）**：如 `https://rom.example.com`，必须能被玩家浏览器打开。
- **下载签名密钥**：和远端 `downloadSecret`（未配置时退回 `token`）一致，至少 16 位。
- **ROM 由浏览器直连远端下载**：总开关。建议先把前三项填好、点「测试连接」通过，
  再打开它。

### 6.4 存量 ROM 迁移（保留原记录 id）

后台"重新上传一次再删旧的"会**新建记录**，收藏、存档、房间、父子版本、封面全部挂在
`roms.id` 上，等于把这些关联切断。用脚本就地迁移：

```bash
# 1) 预演（只读，不动数据库、不上传）
node deploy/migrate-roms-to-remote.mjs
node deploy/migrate-roms-to-remote.mjs --min-size 3        # 只看 ≥3MB
node deploy/migrate-roms-to-remote.mjs --id 32 --id 75     # 指定记录

# 2) 执行：上传 → 远端体积/sha256 校验 → 就地改 storage/remote_file_id/file_path
node deploy/migrate-roms-to-remote.mjs --apply

# 3) 浏览器实测能正常开局后，再自行删除打印出来的本地副本（脚本不会自动删）

# 回滚（整批或按记录）
node deploy/migrate-roms-to-remote.mjs --rollback deploy/migrations/roms-remote-<时间>.json
```

每次成功都会写一条回滚记录（含原始 `file_path`、体积、sha256、远端 id）。

## 七、加载进度（已实现）

- 阶段由真实事件驱动：**读取游戏信息 → 加载资源 → 校验资源 → 初始化模拟器 → 启动完成**，
  没有用定时器编造的百分比。
- 资源任务：核心 js、核心 wasm、当前 ROM、变体依赖的父 ROM、每个 BIOS 文件；
  单项显示名称、已读取/总大小、状态（下载中 / 本地缓存已就绪 / 校验中 / 切换备用地址 /
  已跳过 / 加载失败）。
- **计量口径统一**：进度按"资源本身的体积"算——核心取发布清单的原始体积、ROM 取数据库
  `file_size`、BIOS 取未压缩响应的 `Content-Length`。浏览器给的是解压后的流、而
  `Content-Length` 可能是压缩后长度，所以压缩响应的长度**不会**被当成总长；没有可信总长时
  只显示已读取字节数，不显示百分比（也不会用截断到 100% 掩盖长度错误）。
- 加载面板独立于模拟器组件是否挂载：核心还在下载、模拟器还在初始化时它都盖在画面上，
  直到游戏真的跑起来才消失；失败时显示是哪个资源、什么原因，并给出「重新加载」。
- 换游戏 / 换版本 / 离开页面会开新会话：旧会话的请求被中断、旧回调被丢弃，不会串进度。
- 联机房间里只有**房主**会下载这些资源；客人看的是主机画面，不显示本地进度，也不会
  为了进度提前下载核心。

## 八、上线步骤

### 本机

```bash
cd /www/wwwroot/xbw.ppxin.com
git pull && npm ci
npm run build                              # 前端（含加载进度与后台开关）
node deploy/build-cores.mjs                # 生成发布版本
node --test "tests/*.test.js"              # 105 项回归
sudo systemctl restart games-online        # 后端（版本化核心路由、BIOS 条件缓存）
```

加 nginx `application/wasm`（见 4.3）。

### 远端资源服务器

1. 建 HTTPS 站点（`deploy/nginx/remote-cores.conf` 模板），根目录 `/www/wwwroot/cores`。
2. `deploy/sync-cores.sh` 同步发布目录。
3. 后台开开关、点「测试远端核心」、保存。

### 建议顺序

| 顺序 | 改动 | 生效方式 | 预期效果 | 回滚 |
|---|---|---|---|---|
| 1 | nginx 加 `application/wasm` | `nginx -s reload` | 核心传输 102 MB → 31 MB | 恢复 conf 备份后 reload |
| 2 | 后端 + 前端发布 | `systemctl restart` + `npm run build` | 版本化核心、BIOS 304、加载进度 | `git revert` 后重启 |
| 3 | 核心搬远端 | 后台开关 | 核心流量不再过本机出口 | 关开关（地址会留着） |
| 4 | ROM 签名直连 | 远端补接口 + 后台开关 | ROM 流量不再过本机出口 | 关开关 |

建议 1、2、3 一起做（一个维护窗口），观察一两天带宽曲线后再做 4。

## 九、验收

```bash
# 1) 清单与版本
curl -s https://xbw.ppxin.com/api/cores/manifest | head -c 200

# 2) 本机 gzip 是否生效
curl -sk -o /dev/null -D - -H 'Accept-Encoding: gzip' \
  https://xbw.ppxin.com/api/cores/<版本>/fbneo.wasm | grep -iE 'content-encoding|content-length|cache-control'
# 期望：content-encoding: gzip，content-length 约 9.8 MB（原始 34.4 MB）

# 3) 远端资源服务器（正式验收不要用 -k，证书问题必须暴露出来）
curl -s -o /dev/null -D - https://<远端>/releases/<版本>/fbneo.wasm | \
  grep -iE '^http/|access-control-allow-origin|content-type|content-encoding|cache-control'

# 4) BIOS 条件缓存：第二次应返回 304 且没有正文
curl -sk -o /dev/null -D - -b '<登录 Cookie>' https://xbw.ppxin.com/api/bios/arcade/neogeo.zip
curl -sk -o /dev/null -D - -b '<登录 Cookie>' -H 'If-None-Match: "<上一步的 ETag>"' \
  https://xbw.ppxin.com/api/bios/arcade/neogeo.zip | head -3

# 5) ROM 直连：期望 302 且 Location 指向远端签名地址
curl -sk -o /dev/null -D - -b '<登录 Cookie>' https://xbw.ppxin.com/api/roms/<id>/file | grep -iE '^http/|location'
```

浏览器侧（Chrome DevTools → Network / Application）：

- 核心请求指向远端域名，`Content-Encoding: gzip`，体积与清单一致。
- 加载面板依次显示"加载资源 → 校验资源 → 初始化模拟器"，并在真正开局后消失。
- 第二次进同一个游戏：核心与 ROM 显示"本地缓存已就绪"（Network 里没有大请求）。
- 故意填错远端地址 → 面板显示"正在切换备用地址…"，随后从本机加载成功。

## 十、回滚

| 改动 | 回滚 |
|---|---|
| nginx gzip | `sudo cp nginx.conf.bak-<时间戳> … && nginx -t && nginx -s reload` |
| 远端核心托管 | 后台关掉「启用远端核心托管」并保存（地址会留着，随时能再打开），或把地址改回上一个版本号目录 |
| 远端同步出错 | 远端 `releases/<版本>/` 是原子发布的，改回上一个版本号即可；旧目录不会被脚本删除 |
| ROM 直连 | 后台关掉「ROM 由浏览器直连远端下载」 |
| ROM 迁移 | `node deploy/migrate-roms-to-remote.mjs --rollback <回滚文件>` |
| 前端 | `git revert` + `npm run build`（`frontend/dist` 由 nginx 直出，无需重启后端） |
| 后端 | `git revert` + `sudo systemctl restart games-online` |

## 十一、边界与风险

- **远端是新的单点**：远端挂了但本机文件还在时，浏览器会自动回退本机同版本文件；
  真容灾需要另一份可用副本，代理回退解决不了"源文件本身没了"。
- **代理回退不是容灾**：ROM 直连失败会退回主站代理，但如果远端文件不存在，两者都会失败。
- **HSTS**：站点启用了 HSTS（且带 `includeSubDomains`，见 `server/middleware/security.js`），
  所以资源服务器**必须**用 https，`http://` 的跨域请求会被浏览器拦掉。
- **资源服务器出口带宽与磁盘要单独确认**：它是新的大流量出口，如果与 TURN 中继在同一台
  机器上，联机时两者会互相挤占（见 `deploy/STUN.md`）。
- **压缩只降低传输体积**：不减少浏览器缓存占用，也不减少模拟器内存占用（34 MB 的 wasm
  解压后仍是 34 MB）。真正的内存占用取决于核心本身。
- **CSP**：当前 CSP 只加在 `/api` 响应上，HTML 页面没有 CSP，跨域 `fetch` 不受限制；
  将来若给页面加 CSP，必须把远端域名加进 `connect-src`。
- **git 体积**：`data/cores` 的 32 个核心文件仍被 git 跟踪（`.git` 已 35 MB 量级），
  发布产物 `data/cores-dist` 与 `.gz` 已加入 `.gitignore`。仓库瘦身不在本轮范围内。
- **带宽观测**：本机没装 vnstat/iftop，最省事的办法是采样 `/proc/net/dev` 的 eth0 字节数做差。
- **联机中继**：TURN（`43.248.3.138:14273`）与保存状态上传也会占用主站出口，如果与
  6 Mbps 共享，上面的优化收益会更明显。

## 十二、上线前需要确认（待核实）

- 资源服务器（原记录为 `43.248.3.138`）**面向玩家的实际带宽与线路**：远端只是换了一条
  出口，如果它的出口也很小，收益有限。
- 该机器的剩余磁盘（原记录约 11 GB）：发布目录约 133 MB/版本，ROM 迁出另算。
- 该机器是否已开放 443、是否有可用子域与证书（HSTS 决定了必须 https）。
- 6 Mbps 是上行、下行还是双向共享。
- 远端运行的是 rom-upload 的 **Node 版还是 PHP 版**：决定打哪个补丁、以及
  `downloadSecret` 配在哪份配置里（Node：`config.json` 的 `downloadSecret` 或环境变量
  `DOWNLOAD_SECRET`；PHP：同上）。
